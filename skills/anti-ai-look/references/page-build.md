# Webページを作るときの追加規則

LP・Webサイト・アプリの画面を作るときに、このスキルの他の資料に加えて使う。作る前の決め方（素材・訪問者の用件・覚えて帰る1点）、見出しとラベルの組み方、1画面の量、写真と製品画面の見せ方、動きと操作部品、CSSの実装、ダークモード、グラフの規則をまとめる。

## 1. 規則の強さを3段に分ける

`fixes.md` の5（目的を説明できる表現は使ってよい）を、どの規則に当てはめてよいかで分けたもの。

| 段 | 意味 | 扱い |
| --- | --- | --- |
| 必須 | 正しさ・アクセシビリティ・誠実さに関わる。このファイルでは【必須】と書く | 例外なし。見つけたら直す |
| 既定の癖 | AIが既定で選びがちなもの（このファイルで印の無い規則と、`ui-tells.md` の兆候） | そのページ固有の理由があれば例外にしてよい。理由を記録する |
| 仕上げ | 離れて見ると分からない細部 | 指摘されたら、直すか、直さない理由を一言答える。公開を止めない |

例外の記録のしかた:

- 記録先は CSS の先頭のコメントか、作業報告。何の規則を、どんな事実を根拠に、なぜ外すかを書く（例: `/* 例外: 端末の枠を1つ使う。中身は実際の端末の撮影。この製品は端末の画面そのもの */`）。
- 理由にはそのページの言葉を入れる。「デザイン上の意図」のように別のページにも使い回せる理由は理由として認めない。
- 同じ例外を3回続けて使ったら、それは例外ではなくプロジェクトの方針。デザインシステムか `design.md`（`brand-redesign-review.md` の2）に書く。

## 2. 作る前に決める（追加分）

### 2-1. 素材を先に集め、棚卸しする

- 作り始める前に一度だけ、見せられる素材を聞く: 製品の実際の画面（またはURL・起動方法）、写真、実数値（顧客数、稼働率、価格）、発言者名つきの引用、使ってよいロゴ。答えが無ければ推定して進め、推定した内容を冒頭の1行で伝える。
- 棚卸しを1行で書く。
  - 実在: 依頼とプロジェクトにある具体物（名前、主張、数値、場所、日付、画像）
  - 画像: ページが見せるものと、その出どころ（利用者の写真、製品の撮影、作った見本、ライセンスの明確な写真）
  - 無いもの: もらっていない根拠（ロゴ、引用、数値）
- 無いものは作らない【必須】: 架空の数値、お客様の声、導入企業のロゴの列、導入事例の件数。
- 欠けている事実（会場、日付、価格）は、空欄だと分かる形で置く。例: 破線の枠の中に薄い色で「会場は調整中」。1ページ2か所まで。その事実が無いと訪問者が行動できない場合だけ置き、他は削る。どちらも引き渡しの報告に書く。
- URL が分からないリンクは、ページ内の最も関係する節に向け、必要な URL を報告に書く。架空のURLを作らない。

### 2-2. 訪問者の用件から構成を決める

訪問者がこのページで何をしに来るかを1つ決め、同じ業種の実在サイトが「操作をどこに置くか」「その業種ならではの節」「どう終わるか」に合わせる。決まった型（ヒーローの横に画像、数字の列、3つの手順、メール登録の帯）はソフトウェアのページの形で、他の業種にはほとんど無い（原文の主張。約50の実在サイトを見たとある）。

| 用件 | 操作の位置 | その業種ならではの節 | 終わり方 |
| --- | --- | --- | --- |
| 予約（飲食店・教室・医院） | ナビとヒーローに予約（人数・日・時刻）。メニューや時間割の横にも | 店内や料理の写真、メニュー（昼夜の切り替えか価格つきの行）、時間割、行き方、営業時間と住所 | 営業時間・住所と予約をもう一度 |
| 来店（店舗・ギャラリー・会場） | 今日の営業時間と住所をナビかヒーローに | 開催中のもの、今後の予定（日付順の行）、店の品ぞろえ、アクセス | 来店情報と住所 |
| 参加（イベント・大会・カンファレンス） | 最初の画面からナビにチケット。日付と場所が見出し | 出演者・登壇者（名前を大きく）、日ごとの予定、券種と価格、会場、よくある質問 | チケット、よくある質問 |
| 購入（物販・小さな店） | 商品・価格・選択肢。ヒーローになることが多い | 価格つきの品ぞろえ、使っている場面の寄り、作り方、配送と保証、レビュー（提供されたときだけ） | 商品と価格をもう一度、保証 |
| 試用（アプリ・ゲーム・ツール） | 見出しの直下にストアやダウンロード（対応OSごと） | 製品の実際の画面、機能を画面の場面で見せる、使う前と後、対応環境 | ダウンロードと最後の画面 |
| 申込（SaaS・API・開発者向け） | ナビとヒーローに「無料で始める」と条件の1行。開発者向けはインストールのコマンドが操作になりうる | 動いている製品、できることを場面で、コード例・連携、期間切り替えつきの料金表、よくある質問 | ヒーローの操作をもう一度、またはコード例 |
| 依頼（制作会社・個人・設計事務所） | 連絡先（メール・電話）をナビと実績の後に。フォームは無くてよい | 実績の一覧（名前・依頼主・年・場所）と画像、1件を詳しく、業務内容、所在地 | 連絡先（拠点ごと） |
| 入会（クラブ・コミュニティ） | ヒーローに入会か「初めての参加」 | 活動の様子、日時と場所、会員の種類と価格、初回の案内 | 初回の参加、会員の種類 |
| 視聴・購読（音楽・映画・ポッドキャスト・刊行物・ニュースレター） | 最新作・最新号と、再生・購入・登録のボタン | 作品の中身（曲目・目次）、公演や上映の日程、過去の作品、見本の号 | 日程、過去の作品、登録 |

- ナビの操作ボタンは用件の動詞にする（予約する、チケット、購入する、無料で始める）。
- 最後をメールアドレスの登録欄にしてよいのは、繰り返し届くもの（号、回、公演、刊行）のページだけ。他の用件で最後をメール登録の帯にするのは既定の癖。
- 終わり方の候補（原文は実在サイトで多い順としている）: ヒーローの操作をもう一度 → 実用情報（営業時間・住所・連絡先）→ 続きの一覧 → 短い信頼の材料（保証、掲載、受賞。提供されたものだけ）→ メール登録。

### 2-3. 訪問者が覚えて帰る1点を決める

- その依頼で最も強い実物を、最もよい形で見せたもの。例: その場所そのものの写真、1つの仕事をしている製品の画面、オファーそのものである価格を大きく、実際に試せる操作。
- 最初の画面に置き、報告に1行で書く。
- `decisions.md` の5（主役）は1画面の中の重みの決定。こちらはページ全体で記憶に残るものの決定。数値を記号の並びで表した仕掛けはこれに当たらない。

### 2-4. 隣の依頼でも同じにならないか確かめる

- 同じ業種の隣の依頼（別のパン屋、別の請求書ソフト）でも、構成・ヒーローの形・ナビ・フッター・最初の節がまったく同じ組み合わせになるなら、1つ変えて、何を変えたかを書く。
- 続けて何ページも作るときは、作ったページの構成を記録し、直近3件と同じ構成を避ける。比べるのは記録で、記憶ではない。
- 構成を比べる6つの軸: 見出しの位置 / 本文の組み方 / 区切り方 / ボタンの声（塗り・枠・下線の語・文字だけ・入力欄そのものが操作）/ 画像の扱い / 出現の動き。記録にある1件と4軸以上が同じなら、節の形か順序を変える。
- 既に `design.md` やデザインシステムがあるプロジェクトでは逆に、ページどうしで同じシステムを共有する（`brand-redesign-review.md` の2）。

### 2-5. 作る前に6つの軸で採点する

計画した段階のページを1〜5点で採点し、3点未満の軸があれば作る前に計画を直す。

| 軸 | 3点 | 5点 |
| --- | --- | --- |
| 主張 | 調子がある | 読者が反対できる主張がある |
| 階層 | 二度見しないと順序が分からない | 目を細めて見ても順序が分かる |
| 実装 | 緩い細部が2〜3か所ある | 初回で検査に通る |
| 固有性 | その業種には合う | 他の製品には使えない |
| 抑制 | 飾りが1つ多い | 気に入っていたものを削った |
| 変化 | 直近のページと6軸中3軸が違う | 直近3件とほとんど共通点が無い |

最も低い軸と、取った対策を記録する。全部5点なら、そのために何を削ったかを書く。弱点を作り話で埋めない。

## 3. 見出し・ラベル・句読点

### 3-1. 見出しの上に予告のラベルを置かない【必須】

- 兆候: 見出しの直前にあり、次に来るものの名前を告げるだけの小さな文字。字間を広げた英大文字（`ABOUT` `SERVICE` `FEATURES`）、丸いピル、`01` のような番号、カードの上のカテゴリ札、ロゴの列の上の `TRUSTED BY` など、形を問わない。日本語サイトで多い「英字の小さなラベル + 和文の見出し」もこれに当たる。
- 判定: そのラベルを消して読み直す。失われたのが次に来るものの名前だけなら予告のラベル。事実・行き先・識別子（日付、型番、実在のファイル名）を運んでいるなら残してよい。
- 残してよいもの: 図のキャプション（`<figcaption>`）、表の見出し、入力欄のラベル、ナビやタブの名前、署名や日付、数値の後の単位、コードの実在のファイル名、状態を伝える表示、実在の行き先に向かう告知1つ。
- 消すだけで終えない。見出しが比喩なら、ラベルの言葉を見出しにする（「いつでも、ここに」の上の「営業時間」→ 見出しを「営業時間」にする）。
- 節の始め方の代わり。1ページで1つ、または2つを交互に使う。3つ混ぜると雑然とする。
  1. 何も置かず、見出しから始める
  2. 見出しの最初の言葉で主題を言う（多くの場合これが最良）
  3. 段落の書き出しを少し太くする（別の行にしない）
  4. 意味のある区切り（細線、二重線、色の帯、余白だけ）。区切りの種類は1つにし、節の境目ごとに太さや位置を変える
  5. 本物の数を大きく組む（号数、年、オファーの価格）。1ページ1回まで
  6. 本当に順序がある内容だけ番号つきのリストにする
  7. 上のラベルの代わりに、内容の下にキャプションを置く
  8. 本文の外側の余白に注記を置く
  9. 背景の色を切り替え、その境目を区切りにする
  10. ページの端に続く柱（ランニングヘッド）を置く
  11. 見出しを固定し、内容をその下で流す

### 3-2. 小さな文字を英大文字・広い字間で組まない【必須】

- ラベル・キャプション・表の見出し・ナビ・タグ・チップなど 15px 以下の文字を、全部大文字・スモールキャップス・字間 0.03em 超にしない。本文の書体で一段小さく、通常の大文字小文字で、字間を付けずに組む。
- 例外: ロゴ（ワードマーク）。見出し自体が大文字のデザインで、操作部品を字間 0.04em 以下で合わせる場合。

### 3-3. 等幅の書体を飾りに使わない

ラベル・キャプション・メタ情報・表の見出しに等幅の書体を使うと、技術っぽさの衣装になる。等幅を使うのは、コード・数値・計測値か、見出しや本文自体が等幅のデザインのときだけ。

### 3-4. 見出しの中の1語だけを変えない

- 見出しの中の1語だけを斜体にしない【必須】。
- 1語だけ色・太さ・マーカー・下線で変えるのも既定の癖（予告のラベルの次に多い、機械が作った見出しの形）。日本語の「〇〇を、もっと△△に」で △△ だけ色を変える形も同じ。
- 見出しは1つの太さ・1つの書体スタイル・1つの色で組む。強調したいなら改行するか、2行目を別の大きさにする。

### 3-5. テンプレートの句読点を使わない【必須】

| 兆候 | 代わりに |
| --- | --- |
| メタ情報を中点「·」でつなぐ（`東京 · 2026 · 設計`） | 改行、列、細線で分ける。署名やキャプションの中の「·」1つは可 |
| リンクやボタンの文字の後ろに矢印（`詳しく見る →`） | 操作名を動詞で書く（「料金表を見る」） |
| ラベルの前の飾りの色の点 | 削る。稼働中などの状態を表す点は可（色だけで伝えない） |
| `WORD - 断片` の形のラベル | 文にするか、見出しにする |

和文の「・」で語を並べる普通の書き方はこれに当たらない。

### 3-6. 飾りの文字を置かない

- 意味の無い縦向きの文字、「SCROLL」などのスクロール誘導、ヒーローの版番号や `BETA` のピル、都市名や天気の帯、ヒーローの下の等幅大文字の帯、仮の画像の下のクレジット、タイルの `01 / 4` の数え。
- 事実なら残す（発売日、会場、拠点）。消すと失われる事実は、キャプションかフッターに移す。

### 3-7. 節の見出しは、訪問者が見るものを言う

- 「特徴」「私たちの想い」「選ばれる理由」のような分類名にしない。その節で見られるもの・得られるものを言う（「朝に焼く3種類のパン」）。
- 見出しが競合のページにもそのまま載るなら、この依頼にしか無い名詞で書き直す（`writing-tells.md` の入れ替えテスト）。

### 3-8. 同じ事実を何度も書かない

- 1つの事実（価格、時間、日付、件数）を4つ以上の節に書かない。事実は、それが役に立つ場所で1回だけ言う。
- 節の最後の行で見出しを言い直さない。
- 表や台帳のように、行ごとに同じ値が並ぶのが自然なものは除く。

### 3-9. 主ボタンの横に決まり文句の第2ボタンを置かない

- 「詳しく見る」「今すぐ始める」「デモを予約」を、習慣で主ボタンの横に置かない。第2の操作は、主ボタンと別の行き先があるときだけ、枠線か文字だけで置く。
- 塗りつぶしのボタンを2つ並べない。塗りつぶしの主ボタンの作り方は1ページ1種類（ダイアログは別のページとして数える）。副ボタンは主ボタンより目立たせない。

## 4. 量と構成

### 4-1. 1画面に1つの考え【必須】

- 原文の数値（英語）: 1440px幅の縦900pxの範囲に約80語まで。ヒーローは見出し（7語以内）・1文（12語以内）・操作1〜2個だけ。ページ全体で見える語数は450語まで。節の見出しは6語以内、節の導入は1行、段落は短い2文、リストは4項目まで（それ以上は表にする）。
- 日本語では【推定】語数の代わりに要素の数で守る: ヒーローは「見出し1つ・説明1文・操作1〜2個」、各節は「見出しのまとまり → 主な形（図・表・写真・操作）」の順にする。
- 見出しとヒーローだけを読んで話が通るなら、残りの長さは適切。
- ヒーローの見出し・説明・主ボタン・画像の要点が、1280×800 でスクロールせずに全部見える【必須】。

### 4-2. どの画面にも、その画面の理由を置く

- 1440×900 で1画面ずつスクロールし、各画面に理由になる大きなもの（高さ300px以上の図や写真、3つ並び、3行以上の表やリスト、大きく組んだ主張）があるかを見る。
- 次の状態は直す: 見出しと1行だけの画面、右半分が空いた細い列、ヒーローに比べて小さすぎる節の見出し（1440幅で40px未満）、ヒーローの内容の下と画面の下端の間に160pxを超える空き。
- 直し方は、言葉を足すことでも間隔を詰めることでもない。図を大きくする、本文の幅を広げる、主張を大きく組む、節をまとめる。
- 最後に目を細めて（文字をぼかして）見る。各節に形があり、ページに重い所と軽い所の調子があるか。

### 4-3. 区切りは軽い順に段階を上がる

- 段階: 余白 → 細線（1px）→ 少し色を変えた面（枠なし）→ カード（枠線か影のどちらか）。カードは、それ単独で操作できる内容か、種類の違う内容にだけ使う。
- 節の境目ごとに違う段を使う。すべての境目が同じ区切りと同じ間隔なのはテンプレート。
- カードの中にカードを入れない【必須】。色を変えた面の中に枠つきの箱を入れない。色の付いたページに白いカードを並べない。
- 並んだ数値は、上か縦の細線で区切る（カードにしない）。

### 4-4. 節の間隔と見出しの位置

- 節と節の間隔は、1440幅で120px以上（背景色が変わる境目は64px以上）にし、場所によって変える（原文の値）。
- 見出しの上の余白を、見出しの下の余白の2倍以上にする。見出しが前の内容に近いと、どこの見出しか分からなくなる。
- 文字の入った塗りの箱は、内側の余白を左右 max(8px, 0.5em)、上下 max(4px, 0.3em) 以上にする。スマホでは本文を画面の端から16px離す。

### 4-5. 大きな画面では器を広げない

- 1920×1080 では、内容の器に最大幅（原文は1360〜1520px）を付けて中央に置き、両端の余白（120px以上）だけが広がるようにする。本文の幅、グリッドの列の数、画面幅に比例する画像は増やさない【必須】。
- 確認する幅: `patterns.md` の390pxと1280pxに加え、1280×800（ヒーローが収まるか）、1440×900（ヒーローがちょうど1画面か）、1920×1080（器が保たれるか）。

### 4-6. 製品・写真・図の見せ方

- 実在する製品は、div で組んだ模型ではなく実際の画面の撮影で見せる。URL、起動中の開発サーバー、1つのコマンドで起動できるリポジトリがあれば、起動して、ページの話に合う状態（見本データを入れた、1つの仕事をしている画面）にして撮る。主画面、寄りの詳細、別の画面、スマホ表示を使い分ける。
- 撮った画面は公開前に目で見て、個人名・メールアドレス・トークン・ファイルのパス・エラー表示・開発用の表示が写っていないか確かめる。
- 模型を作るのは、製品がまだ無いか起動できないときだけ。見本の値は見本と分かるもの（`example.com`、「見本食堂」、きりのよい金額）にし、訪問者が実績と受け取れる数字を入れない【必須】。後で撮るべき画面を報告に書く。
- 手で描いたブラウザの枠（3つの丸とURL欄）やOSのウィンドウ枠を使わない【必須】。スマホ・ノートPC・ターミナルの枠は1ページ1つまでにし、中身は実物にする。
- 利用者の画像に置き換える前提の画像枠は、常に何かを表示する（利用者の画像、ライセンスの明確な写真、作った製品の見本）。色を塗っただけの箱やグラデーションの箱（300×200px以上）を写真の代わりに置かない。
- 空の画像枠を1列に4つ以上、1ページに6つ以上並べない（講師6人分の空の顔写真枠など）。名前と役割を文字の一覧や表で組む。「ここにスクリーンショット」のような案内を画面に出さない。
- 物・植物・動物・人・建物・風景のイラストを SVG や CSS で描かない（アイコンの大きさを超えるもの）。SVG を使うのは、1つのセットのアイコン、利用者のロゴ、実データや実在の仕組みの図に限る。イラスト素材集のキャラクター、3Dの塊、アイソメトリックの情景も使わない。
- 数量を同じ記号の並び（1本ずつの瓶、1日ずつの点）で表さない。24個以上並ぶなら数字を大きく組む。
- ヒーローより下で写真がページの約3分の1を超えると、素材写真の展示に見える。強い写真を大きく残し、間の節は文字・表・製品で作る。写真が主役の節を2つ続けない。
- 人物の写真を、顧客・社員・推薦者の代わりにしない。
- 画像のURLを記憶から書かない。利用者の提供物か、ライセンスを確かめた出典のものだけを使い、CC BY などクレジットが必要なものはページに記載する。原文は、Unsplash・Pexels・Pixabay の規約がAIによる画像の選択を禁じているとしている（未確認。使う前に各規約を確認する）。
- ヒーローの画像は最初に描かれる最大の要素なので、`loading="lazy"` を付けない。

## 5. 色（追加分）

- 新しい「AIの定番」に注意する: 生成り（クリーム色）の紙色 + コントラストの強いセリフ体の見出し + テラコッタ（赤土色）のアクセント。温かい・本好き・家族向けの依頼ほど引き寄せられる（原文の判断）。依頼で指定されていなければ、まずアクセントを、次に紙色を、最後に見出しの書体を変え、1軸ずらす。
  - `decisions.md` の「温かい・生活 → 土色、レンガ」と「見出し = 和文明朝」を同時に選ぶと、この3点がそろいやすい。3つ同時には選ばない。
- アクセントの色は面を塗るものではなく合図。画面の約5%以内（今いるナビ項目、フォーカスの枠、主ボタン、グラフで主張する1系列）。色を広く使うなら、「この色を面の30〜60%に使う」のように方針を先に決めて書く。
- 純粋な黒（`#000`）と白（`#fff`）を、変数の定義の外で直接使わない【必須】。背景と文字も基準色にわずかに寄せる。
- 赤と緑だけで状態を区別しない。色の付いた面の上に灰色の文字を置かない。暗い面を塗る CSS のルールでは、同じルールの中で文字色も切り替える。ボタンの文字色はボタンの色と対で定義する。
- 色は OKLCH で定義すると、明度と彩度をそろえやすい（原文は全面的に OKLCH）。

## 6. 文字（追加分）

- 欧文の大きな見出し: 字間は -0.02〜-0.04em（太い書体・幅の狭い書体は 0〜-0.015em）、行間は 1.0〜1.15（1.2 は既定値のまま見える）。全部大文字の見出しが折り返す可能性があるなら、行間を1.0以上にする【必須】。和文の見出しには当てはめない（和文の字間は `ui-tells.md` に従う）。
- 太さはページ全体で3種類まで。離れた組み合わせにする（400と700、300と800）。
- 書体は2系統まで。3つ目を使うなら役割を1つに限る（ロゴ、大きな数字、コードのどれか）。
- 比べる数字には `font-variant-numeric: tabular-nums` を付ける。
- 見出しに `text-wrap: balance`、本文に `text-wrap: pretty` を付け、最後の行に1語だけ残る状態を避ける。`<br>` で改行したら375px幅で確かめる。
- ボタンの文字と主ナビのリンクは、320〜1920pxのどの幅でも折り返さない【必須】。
- 大きな見出しには `overflow-wrap: break-word; min-width: 0` を付ける【必須】。

## 7. 動きと操作部品

### 動き

- `transition: all` を使わない。`width` `height` `top` `left` をアニメーションさせない。動かすのは `transform` と `opacity`【必須】。
- すべてのアニメーションに `prefers-reduced-motion: reduce` の代替を付ける【必須】。
- JavaScript が動かなくても内容が見えるようにする【必須】。出現の演出のために、最初から `opacity: 0` で隠さない。隠すのは、スクリプトが付けるクラスの下（`.js .reveal`）だけにする。
- 出現の動きは1ページ1種類まで、合計0.4〜0.8秒、跳ね返り（バウンス）なし。視差効果、独自のカーソル、カーソルを追う飾り、点滅し続ける点を使わない。
- 時間の目安: 押した・色の変化 120ms、ホバー・ツールチップ・メニュー 220ms、モーダル・引き出し・開閉 420ms。消えるときは現れるときの60〜75%。ブラウザ既定の `ease` を使わない。
- フォーカスの枠は `:focus-visible` で、フェードさせず即座に表示する【必須】。ツールチップは、ホバーでは800〜1000ms待ち、キーボードのフォーカスでは待たない【必須】。
- 自動で切り替わる内容（カルーセル、流れる帯）は、ホバーとフォーカスで止まる。5秒を超えて動くものには停止ボタンを付ける【必須】。
- 自動再生の動画には `muted` を付ける【必須】。`poster` も付ける。

### 操作部品

- 操作部品の8つの状態: 通常・ホバー・フォーカス・押下・無効・処理中・エラー・成功。1つでも欠けたら未完成。
- 無効は3つを同時に: 薄くする（opacity 0.55 程度）、`cursor: not-allowed`、ネイティブの `disabled` 属性【必須】。見た目だけ薄くしない。無効の理由を近くに書く。
- 入力欄の枠線の太さを状態で変えない。フォーカスは `outline` で示す【必須】。入力欄と隣のボタンの高さをそろえる【必須】。
- 処理中はラベルを読めるまま、ボタンの幅を変えない。
- 送信先の無いフォームに「送信しました」「予約を受け付けました」を表示しない【必須】。接続する前は入力の検証だけを行い、「まだ送信先に接続していないため、送信されていません」と書く。必要な送信先を報告に書く。
- 結果が画面で見える操作に、完了の通知（トースト）を出さない。トーストは、失敗したときと、結果が目に見えないときだけ。
- 取り消せる操作は確認なしで実行し、5〜10秒「元に戻す」を表示する。取り消せない操作（アカウント削除など）は確認を残し、消す対象の名前を入力させる。
- 入力欄: プレースホルダーは形式の例（`2026/01/01`）だけにし、指示文にしない。一度触れた欄は離れたときに検証し、その後は入力のたびに検証する。必須の欄は言葉で示す（色だけにしない）。貼り付けを禁止しない。送信ボタンを無効にするのは送信中だけ。送信に失敗したら最初の誤った欄にフォーカスを移す。
- 押せる部品の高さ: 宣伝のページで44〜52px、アプリの画面で32〜40px（当たり判定は44pxに広げる）。ボタンの大きさは2種類まで。

## 8. CSS の実装の約束

- `html` と `body` の両方に `overflow-x: clip` を付ける。`hidden` と `100vw` を使わない（`hidden` は `position: sticky` を効かなくし、`100vw` はスクロールバーの分はみ出す）【必須】。
- 画像の入るグリッドの列は `minmax(0, 1fr)` にする【必須】。縮む必要のある flex の子に `min-width: 0` を付ける。
- ヒーローの高さを `vh` で指定しない。`dvh` か `svh` を使う（スマホのアドレスバーで下が切れるため）【必須】。
- `position: sticky; top: 0` の要素を2つ作らない（節の見出しがナビの下に潜る）【必須】。
- 文字を他の要素の下に描かない（不透明な箱、画像、別の文字が文字を隠す。固定のナビは除く）【必須】。
- 角丸は入れ子の段ごとに1つ。内側の角丸 = 外側の角丸 − 間の余白。
- グリッドの最後の行に1つだけ残る並べ方をしない（数を変える）。ロゴの列は 3 + 3 のように均等に割る（5 + 1 にしない）。
- スマホでは、表の行を特定する列と、操作する列を画面内に残す（行をラベルつきのブロックに組み直すか、最初の列を固定する）。PCで見せている40語以上の内容をスマホで隠さない（ナビは除く）。
- 文書に `lang`、ページ固有の `<title>`、1文の説明（meta description）を付ける。見出しの階層を飛ばさない。`<img>` に `width` と `height` を付ける。
- 選択範囲の色（`::selection`）、入力位置の色（`caret-color`）、スクロールバーの色を、決めた配色に合わせる。

## 9. ライトとダークを両方用意するとき

- 依頼されたときだけ両方を作る。暗い配色1つだけのデザインは、両対応とは別のもの。
- 色はライトの値から1つずつ作り直す。色相はどの色でも動かさない。
- 背景は明度12〜18%で基準色寄り（真っ黒にしない）、文字は明度92〜96%（真っ白にしない）。
- 重なりの高さは影ではなく明るさで表す。1段上がるごとに明度を約3%上げる。カードは背景より明るくする（背景より暗いカードは穴に見える）。ダークでは影を消すか、内側の細線にする。
- アクセントは彩度を下げ（OKLCH の chroma で 0.02〜0.04）、明度を5〜10%上げる。ライトの鮮やかな色は暗い背景でまぶしい。
- 見出しの色は1色にそろえる。
- 原文は、明るい文字は太く見えるので本文の太さを50下げる（400→350）としている。和文フォントには350の太さが無いものが多いので、使う書体で確かめる（未確認）。
- 写真に CSS の `invert` や `brightness` をかけない。
- 切り替えは `data-mode` 属性と `prefers-color-scheme` の両方で行う。選んだモードを保存し、最初の描画の前に読む（違うモードが一瞬表示されないように）。`:root` に `color-scheme: light dark` を付ける。
- コントラストの検査は両方のモードで行う。

## 10. グラフとダッシュボード

- 値が1つなら、大きな数字とその意味を言う言葉で示す（棒1本のグラフにしない）。部分と全体は横の積み上げ棒で示し、円グラフ・ドーナツ・ゲージは使わない。
- 縦軸は1本にする。2軸のグラフは相関を作り出しやすい。単位が違うなら小さなグラフを2つ並べる。
- 主張する1系列だけをアクセントの色にし、他は中立色にする。系列が複数あるならアクセントの明度違いを使い、割り当ての順番を固定する。
- ラベル・値・軸の文字をデータの色で染めない。系列はラベルの横の色見本で示す。
- 格子線は1pxの実線で3〜5本。点線にしない。棒や線に影・3D・グラデーションを付けない。
- 見本データは見本と分かるもの（合計が合う、日付が順に並ぶ）にし、実績と受け取れる値にしない。架空の系列より空欄のほうがよい。
- ダッシュボードは、大きな数字1つ・補助のグラフ1つ・表1つから始める。ゲージを6つ並べたKPIの壁は兆候。
