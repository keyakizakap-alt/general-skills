# 情報源の扱い

## 優先順位と表記

| 順位 | 種類 | 例 | 出典での表記 |
|---|---|---|---|
| 1 | 公式 | 提供元のドキュメント、リリースノート、料金ページ、公式ブログ、官公庁の発表 | 公式 |
| 2 | 一次情報 | 論文、公開リポジトリのコードと Issue、カンファレンスの発表資料、統計の発行元 | 非公式（一次情報） |
| 3 | 専門家・企業の記事 | 実績のある技術者の検証記事、調査会社のレポート、報道 | 非公式 |
| 使わない | 出どころを辿れないまとめ、日付の無いページ、生成されたと見られる量産記事 | — | — |

- 公式でも、マーケティングのページより仕様のページ（ドキュメント、API リファレンス、料金表）を優先する
- 提供元の社員による個人の投稿は、公式発表ではなく非公式として扱う
- 3 しか見つからないときは、その記事が引いている元を辿る。辿れなければ【未確認】にする

## 独立しているかの見分け方

2つの情報源が独立しているのは、それぞれが別に確かめた場合だけ。

- 同じプレスリリースを引いた記事が5本あっても、情報源は1つ
- 公式ドキュメントと、実際に試した第三者の検証記事は独立
- 翻訳記事と原文は1つ
- 公式の英語版と日本語版は1つ。内容が違えば、更新日が新しいほうを採り、違いを書く（翻訳は遅れることがある）

独立した2つ目が見つからない主張は、公式1つで確かめられていれば採用してよい。非公式1つだけなら【未確認】を付ける。

## 日付の読み方

| 日付 | 意味 | 使い方 |
|---|---|---|
| 公開日 | 最初に出た日 | 動向の時期を書くときに使う |
| 更新日 | 最後に直された日 | 仕様や料金が今も有効かの判断に使う |
| 取得日 | 自分が読んだ日 | 出典に必ず書く |

- 更新日の無いページは、本文中のバージョン番号や画面から時期を推定し、【古い可能性】を付ける
- 「最新」「現在」と書かれた記述は、そのページの日付の時点の話として読む
- 予定（提供開始予定、廃止予定）は、予定として書く。実施されたかは別に確かめる

## 食い違いの裁き方

1. 新しさ: 更新日が新しいほう
2. 一次情報か: 提供元に近いほう
3. 具体性: バージョン、日付、条件、再現手順が書かれているほう

採った理由と、退けた内容を「食い違い」の節に一言残す。裁けないときは両方を書き、結論の確からしさを下げる。

## 変わりやすい項目の確かめ方

| 項目 | 確かめる場所 | 落とし穴 |
|---|---|---|
| 料金 | 公式の料金ページ | 地域、通貨、税、無料枠、課金の単位で変わる。条件を一緒に書く |
| 機能ステータス | ドキュメントの該当機能のページ、リリースノート | 発表時は Preview でも後で変わる。原文の語をそのまま書く |
| 提供地域 | 公式の地域別の一覧 | 機能ごと、モデルごとに違う |
| バージョン・廃止予定 | リリースノート、非推奨の一覧 | 廃止日と、新規利用の停止日は別のことがある |
| 利用上限・クォータ | 公式の上限のページ | 契約の種類や申請で変わる |
| 人物の役職、組織名 | 本人または組織の公式ページ | 報道は時点が古いことがある |
| 制度・法令 | 所管官庁のページ、法令の原文 | 解釈は専門家に確認が要る。断定しない |

## 数字の扱い

- 割合には分母、金額には通貨と期間、件数には集計の定義を付ける
- 調査の数字は、調査主体・時期・対象・標本の大きさを書く。提供元が自社製品について出した数字は、そう明記する
- 自分で計算した値は「試算」と書き、式と前提を残す
- 丸めた数字は丸めたと分かるように書く（約、前後）

## 出典の書き方

```
1. タイトル／URL／公式・非公式／取得日 YYYY-MM-DD
```

- URL は取得したページそのもの。トップページや検索結果の URL にしない
- ログインが必要なページ、あとから消える恐れのあるページは、その旨を添える
- 本文で使わなかった資料を出典に並べない。参考として残すなら「参考（本文未使用）」と分ける
