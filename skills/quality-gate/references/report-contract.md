# 完了報告の区別と、不具合修正の進め方

アプリ・Web・コードの作成や修正を終えるときに使う。リスクに比例して適用する。誤字などの軽微な修正、調査、雑談には使わない。

## 完了報告は4つに分けて書く

| 区分 | 意味 | 書くこと |
|---|---|---|
| 実装済み | コードを書いた。動作確認済みとは限らない | 変更したファイル |
| ローカル検証済み | 手元で実行して確かめた | 実行したコマンド、終了コード、操作したシナリオ |
| 本番検証済み | 実際の公開URLで確かめた | URL、確認した時刻、操作、観測結果 |
| 未検証 | 確かめていない | 未実施の確認と、その理由 |

次の言い方は、自分で確認した証拠があるときだけ使う。
- 「全ボタンが動く」「十分にテスト済み」「安全」「本番投入可能」「デプロイ成功」
- ビルドが通っただけでは、画面の操作や本番の動作の証拠にならない。
- `PASS` は、実行した操作・コマンド・観測結果で示せるときだけ書く。示せないものは `NOT_RUN` か `BLOCKED`（足りない権限・認証情報・ツールを具体的に書く）にする。

## 作業の重さに応じた確認

| 作業 | 確認する範囲 |
|---|---|
| 文言・誤字などの軽微な修正 | 関係する検査だけ。セキュリティ監査は求めない |
| 操作（ボタン・フォーム・遷移・保存）が変わる | 影響する操作フローと、隣接する回帰しやすいフローを実際に操作する |
| 公開前 | 主要フローのE2E、証拠、セキュリティ確認（秘密情報・認可・依存パッケージ）、実際の公開URLでの再確認 |
| 文書・資料など、コードでない成果物 | Web の E2E ではなく、実際の見た目とリンクを確認する |

- 公開URLの確認は、ローカルの確認で代用しない。ローカル検証と本番検証は別の行に書く。
- 重大な変更や公開では、別の文脈の確認役（読み取り専用のサブエージェント、別のAI、静的解析など）を使う。使えなかったときは「独立レビュー未実施」と書き、使ったと書かない。

## 不具合を直すときの順序

1. 再現: 再現手順と失敗の様子を、直す前に確認する。
2. 根本原因: 原因を、ログ・コード・再現結果などの根拠つきで特定する。表面的な対処を重ねない。
3. 最小の修正: 原因に対する最小の変更にとどめる。
4. 回帰テスト: 同じ不具合を検出するテストを足す。足せないときは理由を書く。
5. 再検証: 失敗した経路と、隣接する経路を再実行する。ローカルと本番を別々に確認する。

結果は `references/evidence-report-template.md` の表に書く（複雑な作業・公開のとき）。軽微な作業は、最終回答に同じ区分の短いチェックリストを書けば足りる。
