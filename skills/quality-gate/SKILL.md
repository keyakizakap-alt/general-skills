# quality-gate

**目的**: 「テストを実行してから完了報告」「資料は見直してから納品」を、指示の読み落としに頼らず毎回実行させる。

## 1. 環境を見分ける

- ファイルを書けてコマンドを実行できる（Claude Code）→ 2 と 3
- ファイルを書けない（claude.ai のチャットなど）→ 4

## 2. プロジェクトに検査コマンドを登録する（Claude Code）

1. 検査コマンドを決める。README、`AGENTS.md`、`package.json` の `scripts.test`、`Makefile` の `check`/`test`、`tests/` の有無から探し、利用者が示したものを最優先にする。推測で決めたときはそう伝え、実行して終了コード0を確かめてから登録する。
2. プロジェクトの `.claude/quality-gate.json` に書く。

   ```json
   {"command": "python3 -m unittest discover -s tests", "timeout": 600, "max_retries": 3}
   ```

   - `command`: プロジェクトのルートで実行する。終了コード0が合格
   - `timeout`: 秒。既定600
   - `max_retries`: 同じセッションで続けて失敗したとき、作業の継続を求める上限回数。超えたら警告だけ出して止める。既定3
3. このファイルをコミットすると、general-skills プラグインを有効にした全員のセッションで、応答の終わりに検査が走る。失敗すると Claude は停止せず修正を続ける。前回成功したときから作業ツリーが変わっていなければ実行しない。
4. 確認の手間を減らすなら、同じコマンドをプロジェクトの `.claude/settings.json` の `permissions.allow` に `Bash(<コマンド>)` として追加するよう提案する（権限の変更なので、利用者の承認を得てから書く）。

一時的に止めるときは、環境変数 `QUALITY_GATE_DISABLE=1` を設定する。

信頼できないリポジトリでは、`.claude/quality-gate.json` のコマンドがそのまま実行される点に注意する。開く前に中身を確認する。

## 3. 資料・文章を見直す（Claude Code）

検査コマンドで判定できない品質は、作成者と別の文脈で確認させる。

| 対象 | 確認役 | 渡すもの |
|---|---|---|
| 資料の見た目（PPTX・PDF・HTML） | `design-reviewer` | ページ画像のパス、規約、ページ数 |
| Web・アプリの画面 | `ui-checker` で撮影 → `design-reviewer` | スマホ幅・PC幅のスクリーンショット、画面の目的、デザインシステム |
| 数字・仕様・製品名・日付 | `fact-checker` | 主張の一覧と元資料 |
| 差分全体・合格条件 | `deliverable-reviewer` | 合格条件、差分、検査結果 |

確認役の指摘を直したら、2 の検査コマンドをもう一度通す。

## 4. ファイルを書けない環境（チャット）

フックは動かないので、同じ検査を手順として実行し、結果を表で示す。

1. 合格条件を列挙する（依頼文、利用者の規約、無ければ「依頼に答えているか・事実と推測の区別・数字の出典と参照日・依頼外の変更」）。
2. 成果物を条件ごとに確認し、成功 / 失敗 / 未確認と根拠を書く。
3. 資料なら、上の design-reviewer の観点（番号のゼロ埋め、同じ配置の反復、はみ出し、抽象的な見出し、装飾、根拠）で見直す。
4. 事実は一次情報で確かめ、確かめられないものは「未確認」と書く。

## 報告

| 検査 | 結果 | 根拠 |
|---|---|---|

結果は成功 / 失敗 / 未実行 で書く。実行していない検査を成功と書かない。
