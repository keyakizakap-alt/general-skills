# Prompt Architect

**目的**: 追加のヒアリングをほぼせずに、そのままコピペして業務で使えるプロンプトを1回の応答で完成させる。

**設計思想**
1. プロンプトの品質は「文才」ではなく**決定した項目の数**で決まる。曖昧さが残る箇所は、聞き返す前にまず既定値を置いて埋め、前提として明示する。ユーザーは前提を読んで直すだけで済む。
2. **減算優先** — モデルが賢くなるほど良いプロンプトは短くなる。足場（手順の細分化、CoT指示、大量の例、強い語調）は古い世代のための補助輪であり、能力が上がったら**足すのではなく外す**。詳細は `references/model-growth.md`。

## 実行手順

### Step 0. インテーク（頭の中で30秒・質問しない）

依頼文から次の7変数を確定する。書かれていなければ**最も実務的な既定値を推論**し、Step 5 の「前提」に必ず列挙する。

| 変数 | 内容 | 不明時の既定値 |
|---|---|---|
| `GOAL` | 何を出させるか（成果物の型） | 依頼文の名詞から最も具体的な成果物を選ぶ |
| `USER` | 誰が使い、誰が読むか | 「依頼者本人が業務で使う／読み手は社内関係者」 |
| `INPUT` | 毎回差し込むデータは何か | 変数 `{{...}}` として1〜3個切り出す |
| `DONE` | 成功条件（検証可能な形） | 「後工程がそのまま使える」＝手直し不要 |
| `SURFACE` | 実行環境：チャット単発 / API組込み / エージェント（ツールあり） | チャット単発。ただしツール・自動実行の語があればエージェント |
| `RISK` | 誤りのコスト、機密・個人情報の有無 | 中。社外送付・法務・金額計算が絡めば高 |
| `TIER` | 宛先モデルの能力段階（T0軽量 / T1標準 / T2推論内蔵 / T3自律エージェント） | **T2**。社内小型モデル・組込み用途なら T1、ツール自律実行なら T3 |

**質問してよいのは1ケースだけ**: どの解釈を取るかで成果物が**別物になる**とき。その場合も「A案で作った完成プロンプト」を先に出し、最後に1問だけ添える。止めて聞かない。

### Step 1. アーキタイプを選ぶ

`references/archetypes.md` から最も近い型を1つ選ぶ（調査・分析／要約・議事録／分類・抽出／文書作成／レビュー・批評／顧客対応／変換・翻訳／コード／エージェント／LLM評価者）。
各型には「必ず落とし穴になる項目」が書いてある。**選んだ型の落とし穴は必ずブロックに反映する。**

### Step 2. 9ブロックを組み立てる

順序を守る。文例と書き分けは `references/blocks.md`。

1. **役割** — 誰として振る舞うか（1〜2文。肩書きだけでなく判断基準を含める）
2. **目的と成功条件** — 何のための出力か＋「完了とみなす条件」を検証可能な形で
3. **前提・制約** — 背景、対象読者、禁止事項の**理由**（理由を書くと一般化して守る）
4. **入力** — `{{変数}}` と区切り（`<input>…</input>` か `---`）。データと指示を物理的に分離
5. **手順** — 順序や網羅性が結果を左右するときだけ番号付きで。不要なら書かない
6. **ルール** — 「〜するな」ではなく「〜せよ」で書く。数値で縛れるものは数値で
7. **出力形式** — 構造・長さ・語調。機械処理ならスキーマを明示し、余計な前置きを禁止
8. **品質・不確実性プロトコル** — 根拠の示し方、推測と事実の分離、情報不足時の振る舞い（後述の必須句）
9. **例** — 3〜5件。多様性を持たせ、境界事例を1つ入れる。ある場合のみ

**ブロックの取捨**: 1・2・4・7・8は原則必須。3・5・6・9はタスクが要求するときだけ。**使わないブロックは書かない**（空ブロックはノイズになり、モデルの追従を下げる）。

### Step 3. 能力ティアで適合させる（モデル名で分岐しない）

モデル名は陳腐化するが、能力の段階は残る。`TIER` に応じて層を当てる（詳細表: `references/model-growth.md`）。

| ティア | 設計の重心 | この層でやること |
|---|---|---|
| **T0** 軽量・ローカル | 引き出す | 1文1命令、手順5つ以内、例5件以上、否定形を使わない、出力形式は1種類 |
| **T1** 標準 | 形を作る | 9ブロックを厚めに。手順と例をしっかり書く。CoT指示が効く |
| **T2** 推論内蔵（既定） | **抑える** | CoT指示と強い語調を削除。出力長を数値で指定。スコープ固定と完了条件を明示。形式強制はAPIのスキーマ機能へ委譲 |
| **T3** 自律エージェント | 境界を引く | T2 + ブロック10〜13（ツール方針・停止条件・状態管理・エスカレーション）。`references/agents.md` 必読 |

ティアが不明な新しいモデルは、`assets/capability-probe.md`（5〜10分のプローブ）で判定する。

そのうえで、宛先が特定されているときだけ `references/targets.md` のベンダー固有の上乗せを当てる。
**共通で守ること**: 本文は素のテキスト＋見出し（最大公約数）／長い入力は先・要求は末尾／出力の長さは数値で指定／矛盾する指示を残さない。

### Step 4. セルフ検査（納品前に必ず）

`references/pitfalls.md` のチェックリストで自己採点する。機械的に確かめたいときは:

```bash
python3 scripts/lint_prompt.py <生成したプロンプトのファイル>            # 必須・推奨項目
python3 scripts/lint_prompt.py <ファイル> --tier T2                      # そのティアで不要な足場が残っていないか
```

コード実行が使えない環境（claude.ai でコード実行が無効、Webのチャットに貼って使う等）では、
`references/pitfalls.md` の「納品前チェックリスト」を目視で1項目ずつ当てる。スクリプトはあくまで補助。

**1つでも落ちたら直してから出す。** 特に頻出の3つ:
- 成功条件が「良い感じに」「適切に」で終わっていないか（→ 検証可能な条件に置換）
- 禁止だけ書いて代わりの行動を指定していないか（→ Do 形式に書き換え）
- 情報が足りないときの振る舞いが未定義でないか（→ 下の必須句を入れる）
- T2以上なのに古い足場（「段階的に考えて」「必ず」「CRITICAL」「迷ったらツールを使え」）が残っていないか（→ 削除）

### Step 5. 納品フォーマット

必ずこの4点を、この順で出す。

1. **完成プロンプト** — 単一のコードブロック。コピペしてすぐ動く。説明文を混ぜない
2. **前提（Assumptions）** — Step 0 で自分が決めた既定値を箇条書き。「違う場合はここを直す」と明示
3. **調整ノブ** — 出力が長い/短い、堅い/砕けた、厳しい/緩い等、1行で差し替えられる箇所を3つ程度
4. **使い方と検証** — どこに貼るか（システム欄かユーザー欄か）、**想定した能力ティアと、別ティアに移すときの調整点**、初回に試す入力例、出力を確認する観点2〜3個

## どのプロンプトにも入れる必須句

タスクが何であれ、実務用なら次の2つは既定で入れる（不要と判断したら理由を前提に書く）。

**不確実性プロトコル**（捏造を防ぐ。実務事故の最大要因）
```
与えられた情報だけでは確定できない点は、推測で埋めずに「要確認」として末尾に箇条書きで挙げる。
事実と推測を混在させず、推測を述べる場合は「推測」と明記する。出典がある場合は出典を併記する。
```

**スコープ固定**（勝手な拡張・省略を防ぐ）
```
依頼された範囲だけを扱う。範囲を広げる提案がある場合は成果物に混ぜず、末尾に「提案」として分けて書く。
指示された項目は省略せず、扱えなかった項目はその理由を明記する。
```

`RISK` が高い場合はさらに `references/blocks.md` の「機密・安全ブロック」を追加する。

## 既存プロンプトの改善を頼まれた場合

1. 9ブロックのどれが欠けているかを表で示す（欠落 → 起きる不具合、の形）
2. 改善版を全文で出す（差分だけ渡さない。コピペできないと使われない）
3. 変更点を3〜5行で説明する

---

## モデルが新しくなったとき（プロンプトの棚卸し）

「新しいモデルに乗り換えた」「精度が落ちた気がする」「昔作ったプロンプトを見直したい」と言われたら、
**追記ではなく削除から始める**。手順は `references/model-growth.md`。要点:

1. 代表入力15〜30件でベースラインを取る
2. 足場を全部外した**最小版**（目的・入力・出力形式・品質基準のみ）でも測る
3. 最小版で失敗した項目だけ、1つずつ戻して再測定する
4. 残った失敗にだけ追記する（足すのは最後）
5. 削除して退行しなかった項目は二度と戻さない

最初に外す候補: 「段階的に考えて」等のCoT指示 / 形式模倣のための大量の例 / 「必ず」「CRITICAL」「迷ったらツールを使え」 /
長い役割演技 / 防御的な再掲 / 出力整形の自前強制（スキーマ機能へ委譲） / 過剰な手順分解。

逆に、世代が上がるほど**重要になる**もの（減らさない）: 完了条件・停止条件・確認条件 / スコープ固定 / 出力長の明示 /
根拠と自己検査 / 状態の外部化。

## このスキル自身の鮮度管理

- モデル名・バージョン固有の記述は `references/targets.md` にのみ置く。他のファイルには書かない（原則だけを書く）
- `targets.md` の各項目には**出典と参照日**を付ける。**90日経過または世代交代で再検証**し、未再検証の項目は断定しない
- 新世代の情報を足すときは、古い世代向けの記述を削除するか対象ティアを明記する。**積み上げない**
- 未知のモデルに出会ったら `assets/capability-probe.md` でティアを判定し、確認した仕様を参照日つきで `targets.md` に追記する
