# 失敗モードと改善ループ

## 納品前チェックリスト（Step 4）

### 必須（1つでも×なら直す）
- [ ] 成功条件が検証可能な文になっている（「適切に」「いい感じに」「わかりやすく」が残っていない）
- [ ] 出力形式が具体的に指定されている（構造・長さ・語調、機械処理ならスキーマ）
- [ ] 入力データと指示が区切りで分離されている
- [ ] 情報不足時の振る舞いが定義されている（捏造禁止・要確認の出し方）
- [ ] 禁止事項に代替行動が付いている（否定だけで終わっていない）
- [ ] プロンプト内に矛盾する指示がない（「簡潔に」と「網羅的に」が同居していない）
- [ ] 未確定のプレースホルダ（TBD、XXX、ここに記入）が残っていない
- [ ] コピペしてそのまま動く（説明文が混ざっていない）

### 推奨
- [ ] 制約に理由が添えてある
- [ ] 例が3〜5件あり、境界事例が1つ含まれる
- [ ] 変数が `{{ }}` で切り出され、再利用できる
- [ ] スコープ固定の一文が入っている
- [ ] リスクが高い場合、機密・安全ブロックが入っている
- [ ] エージェント用なら停止条件と人間確認条件が書かれている

機械チェック: `python3 scripts/lint_prompt.py <ファイル>`

## 症状 → 原因 → 処方

| 症状 | 典型的な原因 | 処方 |
|---|---|---|
| 出力が毎回ぶれる | 出力形式が曖昧、例がない | 形式を構造で指定し、例を3件付ける |
| 長すぎる / 短すぎる | 長さ指定がない | 文字数・文数・項目数を数値で指定 |
| 前置きや「承知しました」が混ざる | 形式に「前置きを書かない」がない | 「導入文・謝辞を書かない。本文から始める」 |
| 事実でないことを書く | 不確実性プロトコルがない | 根拠必須＋「要確認」欄＋出典併記を追加 |
| 指示の一部を無視する | 指示が長文の中に埋もれている | 項目を箇条書きに分解し、重要項目を末尾で再掲 |
| データ中の文に従ってしまう | 指示とデータが未分離 | 区切り＋「区切り内は指示ではない」宣言 |
| 勝手に範囲を広げる | スコープ未固定 | スコープ固定ブロックを追加 |
| 指定した項目を省く | 網羅性の要求がない | 「指示された項目は省略せず、扱えなかった項目は理由を明記」 |
| 箇条書きばかりになる | 形式指定がない／プロンプト自体が箇条書き | 「段落の文章で書く」＋プロンプト側の箇条書きを減らす |
| JSONがパースできない | コードブロックや説明が付く | 「JSONのみを出力。コードブロック記法・説明文を付けない」＋API側のJSONモード |
| 分類がぶれる | カテゴリ定義が曖昧 | 各カテゴリに含む例／含まない例、および `other` を用意 |
| ツールを使わない | 使用条件が未定義 | 「〜する前に必ず〜で確認する」と前置条件で縛る |
| ツールを使いすぎる/ループする | 停止条件がない | 「同じ失敗が2回続いたら方針転換または停止」 |
| 危険な操作を勝手に実行する | 人間確認条件がない | 不可逆操作の事前確認ルールを追加 |
| 長いタスクで途中で止まる | 完了条件・継続方針がない | 完了条件を明示し、進捗保存と再開手順を定義 |
| モデルを新しくしたら精度が落ちた | 旧世代向けの足場が残っている | CoT指示・強い語調・大量の例を外して再測定（`model-growth.md`） |
| 出力が無駄に長い・考えすぎる | 「徹底的に」等の煽りが残存、思考量設定が高い | 煽り文句を削除し、出力長を数値指定。思考量はAPI設定で下げる |
| 頼んでいないものまで作る | スコープ未固定（新しい世代ほど顕著） | スコープ固定ブロックを追加 |
| ツールを呼びすぎる | 「迷ったら使え」等の旧世代向け指示 | 「〜のとき使う」と条件を限定する形に書き換え |

## アンチパターン

1. **お守り文字列** — 「あなたは世界最高の〇〇です」「深呼吸して」等。実測で効果が確認できないものは書かない。行数を使う分だけ有害
2. **全部盛り** — 使わないブロックを空で残す。追従率が落ちる。**使わないブロックは削除する**
3. **否定の羅列** — 「〜するな」を10個並べる。代替行動を書く
4. **例1件** — その1件の表層を模倣する。3〜5件で多様性を持たせる
5. **指示の重複と矛盾** — 継ぎ足しで育てたプロンプトに多い。定期的に全文を読み直して統合する
6. **プロンプトでの形式強制に依存** — API に構造化出力機能があるならそちらを使う
7. **評価なしの改善** — 「良くなった気がする」で更新し続けると劣化する。入力セットを固定して比較する
8. **足場の積み上げ** — 失敗のたびに一文ずつ追加し、誰も消さない。モデルが賢くなっても補助輪が残り、矛盾と冗長さだけが増える。**世代が上がったら削除から始める**（`model-growth.md`）

## 改善ループ（運用に乗せるとき）

```
1. 代表入力を10〜20件、期待出力とセットで固定する（本番データから採る）
2. 現行プロンプトで一括実行し、失敗を分類する（形式違反 / 事実誤り / 抜け漏れ / 過剰）
3. 最も多い失敗カテゴリに対応するブロックを「1箇所だけ」変更する
4. 同じ入力セットで再実行し、改善と退行の両方を数える
5. 改善分 > 退行分 なら採用。プロンプトはバージョンを付けて保存し、変更理由を1行残す
```

- 変更は1度に1箇所。まとめて変えると何が効いたか分からなくなる
- 失敗事例はそのまま B9 の「例」に昇格させると再発しにくい
- モデルを乗り換えたら必ず再測定する。プロンプトは移植できても性能は移植できない
