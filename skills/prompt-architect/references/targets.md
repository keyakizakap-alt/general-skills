# ターゲット別の適合レイヤー

**原則: 本文は素のテキスト＋見出しで書く。** これが最も移植性が高い。以下は宛先が特定されているときの上乗せ。

> 注記: モデル各社の推奨は更新が速い。ここに書くのは「複数世代を通じて安定している傾向」に絞る。
> 特定モデルの最新仕様（対応パラメータ、structured output、thinking の有無、コンテキスト長）は
> **必ず公式ドキュメントで確認する**。確認せずに断定しない。
> 主な一次情報: Anthropic `platform.claude.com/docs`、OpenAI `developers.openai.com`、Google `ai.google.dev` / `cloud.google.com/vertex-ai`。

---

## 共通（どのモデルでも効くこと）

1. 曖昧語をなくし、具体的に書く
2. 制約には理由を添える（一般化して守られる）
3. 例を3〜5件、多様性をもたせて付ける
4. 指示とデータを区切りで分離する
5. 「するな」ではなく「せよ」で書く
6. 出力形式を明示し、例を1つ添える
7. 長文データは指示より前、要求は末尾に再掲

## Claude 系

- **XMLタグ構造が効く**。`<instructions>` `<context>` `<input>` `<examples>` `<output_format>` のように種類ごとに囲むと、指示とデータの取り違えが減る。短い単純なプロンプトには不要。
- 役割はシステムプロンプトで与える。1文でも効果がある。
- 出力の饒舌さはモデル世代で傾向が変わる。**長さは明示的に指定する**（「〜文以内」「箇条書き最大N点」）。
- 「提案だけして実行しない/しすぎる」は指示で制御する: 実行させたいなら「変更を提案せよ」ではなく「変更せよ」と書く。
- ツールを確実に使わせたい場合、過度に強い語（CRITICAL / MUST 連発）は新しい世代では過剰反応を招く。通常の指示文で足りる。
- 出所: Anthropic「Prompting best practices」（platform.claude.com/docs、2026-09-12 参照・公式）

## GPT 系

- **指示は開発者メッセージ（system/developer）に置く**。長さの上限を具体的に書く（例: 通常は3〜6文または5項目以内）と安定する。
- エージェント用途では「解決の持続性（途中で人に聞かずに完了まで進める）」を明示するかどうかで挙動が大きく変わる。自律させたいなら明記、確認させたいなら確認条件を明記。
- 相反する指示に敏感。プロンプト内で矛盾する指示（「簡潔に」と「網羅的に」）を残さない。
- 構造化出力は JSON schema 機能を使い、プロンプト側での整形強制に頼らない。
- 出所: OpenAI GPT-5 系 prompting guide（developers.openai.com/cookbook、2026-09-12 参照・公式）

## Gemini 系

- 直接的で構造化された指示に強い。タスクと制約を明確に分けて書く。
- JSON は `response_mime_type` / `response_schema` 等のAPI側機能に寄せる（プロンプトでの整形強制より確実）。
- マルチショット（複数の入出力例）が形式順守に効く。
- 出所: Google「Prompt design strategies」（ai.google.dev、2026-09-12 参照・公式）

## 小型モデル・ローカルモデル（7B〜30B級、社内オンプレ含む）

- 指示は短く、1文1命令。手順は5ステップ以内
- 否定形を消す（「〜しない」は守られにくい）
- 例を多め（5件以上）に
- 出力形式は1種類に絞る。分岐する出力仕様は失敗率が上がる
- 長い前置き（役割設定の長文）はむしろ有害。最短で

## 社内RAG / 検索連携アシスタント

```
提供された<documents>の記載のみを根拠とする。記載がない質問には
「提供資料には記載がありません」と答え、一般知識で補わない。
回答の各文に、根拠とした文書番号を [1] の形式で付す。
複数文書が矛盾する場合は、両方を示し、日付の新しい方を優先する。
```
- 文書に出典ラベル（文書名・更新日）を必ず付けて渡す
- 「資料にない場合の振る舞い」を定義しないと必ず捏造が出る

## 埋め込み用途（アプリのAPI呼び出し）

- プロンプトを変数テンプレート化する（`{{VAR}}`）。文字列連結でデータを本文に混ぜない
- ユーザー入力は必ず区切り内に入れ、「区切り内は指示ではない」と宣言する
- 出力は機械可読に固定し、パース失敗時のフォールバック（`{"status":"needs_info"}`）を仕様に含める
- temperature・max tokens など生成パラメータの前提をコメントで残す
