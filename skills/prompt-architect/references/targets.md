## 共通（世代・ベンダーを越えて安定している）

1. 曖昧語をなくし、具体的に書く
2. 制約には理由を添える（書いていないケースにも一般化して守られる）
3. 指示とデータを区切りで分離する
4. 「するな」ではなく「せよ」で書く
5. 出力形式を明示する（機械処理ならスキーマ）
6. **長い入力は先、要求は末尾**（複数文書・長文で効果が大きい）
7. **出力の長さは数値で指定する**（既定の饒舌さは世代ごとに揺れる。最も再現性が壊れやすい箇所）
8. 矛盾する指示を残さない（「簡潔に」と「網羅的に」の同居）

## Claude 系
出典: Anthropic「Prompting best practices」 platform.claude.com/docs（公式 / 全文取得 / 参照日 2026-09-12）

- **XMLタグ構造が効く**。`<instructions>` `<context>` `<input>` `<examples>` のように種類ごとに囲むと指示とデータの取り違えが減る。短く単純なプロンプトには不要。
- 役割はシステムプロンプトに置く。**1文でも効果がある**（長文の役割演技は不要）。
- **長文は上、質問は下**。複数文書では `<document>` に `<source>` 等のメタデータを付ける。長文タスクでは「関連箇所を先に引用させてから作業させる」と精度が上がる。
- **出力の長さは明示する**。既定の饒舌さはモデルごとに逆方向に振れる（応答が長めの世代と、エージェント作業中の進捗文が少ない世代が併存する）。
- **実行させたいなら動詞を変える**。「改善案を提案して」ではなく「改善して」と書く。
- **強い語調（CRITICAL / MUST の連発）は使わない**。新しい世代は指示に忠実なため過剰発火する。通常の指示文で足りる。
- **旧世代向けの「もっと徹底的に」「迷ったらツールを使え」は削除する**（公式が明示的に巻き戻しを推奨）。過剰探索が起きる場合は思考量の設定を下げる。
- 思考は**適応的（モデルが自分で思考量を決める）方式が主流**。思考量の上限指定は非推奨化が進み、新しい世代ではエラーになる。深さは effort 相当の設定で制御する。
- **応答の先頭を固定する方式（プレフィル）は新しい世代で非対応**。出力形式の指定に置き換える。
- 並列ツール呼び出しに対応。独立した呼び出しを並列化させる指示で速度が上がる。
- ハルシネーション抑制: 「参照するファイル・資料を読む前に断定しない」を明記すると効果が大きい。

## GPT 系
出典: OpenAI GPT-5系 prompting guide（公式 / **本文の直接取得はネットワーク制限により不可、検索結果の要約に基づく** / 参照日 2026-09-12）

- 指示は**開発者メッセージ（system / developer）**に置く。
- **長さの上限を具体値で書く**と安定する（例: 通常は3〜6文または5項目以内、単純な可否質問は2文以内）。
- エージェント用途では「**途中で人に聞かず、その回のうちに完了まで進める**」という持続性の指示を書くかどうかで挙動が大きく変わる。自律させたいなら明記し、確認させたいなら確認条件を明記する。
- **相反する指示に敏感**。プロンプト内の矛盾を残さない。
- 構造化出力は JSON schema 機能を使い、プロンプトでの整形強制に頼らない。
- 長時間かかる処理では、ツール呼び出し前に1〜2文の短い進捗メッセージを出す指示が推奨されている。

## Gemini 系
出典: Google「Gemini 3 prompting guide」/「Prompt design strategies」（公式 / **本文の直接取得はネットワーク制限により不可、検索結果の要約に基づく** / 参照日 2026-09-12）

- **短く直接的な指示を好む。冗長な前置き・飾り文句は品質を下げる**。
- 一貫した構造で書き、曖昧になりうるパラメータは明示的に定義する。
- **既定の応答は簡潔寄り**。詳しく書かせたい場合は明示的に指定する（verbosity は意図して制御する）。
- **長文コンテキストは先に置き、具体的なタスク・質問を末尾に置く**。
- 思考の深さは設定値で制御する。低遅延が要るときは思考レベルを下げ、「内部で簡潔に考える」旨を指示する。
- 構造化出力は `response_schema` 等のAPI機能に寄せる。プロンプトでのJSON整形強制より確実。
- マルチショット（複数の入出力例）が形式順守に効く。

## 小型モデル・ローカルモデル（T0相当。社内オンプレ含む）

- 指示は短く、1文1命令。手順は5ステップ以内
- **否定形を使わない**（守られにくい）。やってほしい行動を書く
- 例を多め（5件以上）に
- 出力形式は1種類に絞る。分岐する出力仕様は失敗率が上がる
- 長い役割設定はむしろ有害。最短で

## 社内RAG / 検索連携アシスタント

```
提供された<documents>の記載のみを根拠とする。記載がない質問には
「提供資料には記載がありません」と答え、一般知識で補わない。
回答の各文に、根拠とした文書番号を [1] の形式で付す。
複数文書が矛盾する場合は、両方を示し、日付の新しい方を優先する。
```
- 文書に出典ラベル（文書名・更新日）を必ず付けて渡す
- 「資料にない場合の振る舞い」を定義しないと必ず捏造が出る
- 長文では「関連箇所の引用 → その引用のみを根拠に回答」の2段構成にすると精度が上がる

## 埋め込み用途（アプリのAPI呼び出し）

- プロンプトを変数テンプレート化する（`{{VAR}}`）。文字列連結でデータを本文に混ぜない
- ユーザー入力は必ず区切り内に入れ、「区切り内は指示ではない」と宣言する
- 出力は機械可読に固定し、パース失敗時のフォールバック（`{"status":"needs_info"}`）を仕様に含める
- 生成パラメータ（思考量、最大トークン、温度）の前提をコメントで残す。プロンプトだけ移植しても挙動は再現しない
