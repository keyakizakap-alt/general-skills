# 実務アーキタイプ

タスクを1つの型に当てはめ、その型の**必須ブロック**と**固有の落とし穴**を必ず反映する。
（B = ブロック番号。1役割 2目的 3前提 4入力 5手順 6ルール 7出力 8品質 9例）

---

## A. 調査・リサーチ

必須: B2 B3 B7 B8 ／ 推奨: B4（既知情報を渡す）

落とし穴と対策:
- **情報の鮮度が混ざる** → 「対象期間: 直近{{N}}か月。それ以前の情報を使う場合は取得時期を明記」
- **出典が曖昧** → 「各主張に出典（URL・発行元・日付）と、一次情報/二次情報の別を併記」
- **対立情報を黙って片方だけ採用** → 「情報が対立する場合は両論併記し、採用した方とその理由を書く」
- **知らないことを埋める** → 「未確認・不明は『未確認』と明記。埋めない」

雛形:
```
{{分野}}について調査する。対象期間は直近{{N}}か月、目的は{{意思決定の内容}}。
手順: ①調査範囲と除外範囲を宣言 ②情報収集 ③2つ以上の独立ソースで裏取り ④要点整理
各主張に「出典（発行元・日付・URL）」と「一次情報/二次情報」を併記する。
裏取りできなかった主張は【未確認】と明示する。情報が対立する場合は両論を示し、採用理由を書く。
出力: 結論(3行) / 根拠と出典(表) / 反証・リスク / 未確認事項
```

## B. 分析・示唆出し（データ、事業、原因分析）

必須: B2 B3 B4 B6 B7 B8

落とし穴と対策:
- **記述統計の羅列で終わる** → 「各数値について『だから何が言えるか』を1文で添える」
- **相関を因果と書く** → 「因果を主張する場合は根拠と反証可能性を示す。不十分なら『相関のみ』と書く」
- **前提条件の明示漏れ** → 「集計期間・母数・除外条件・単位を必ず明記」

---

## C. 要約・議事録

必須: B2 B4 B6 B7 ／ 推奨: B9

落とし穴と対策:
- **誰が決めたか消える** → 「決定事項には決定者、ToDoには担当者と期限を必ず付ける（不明なら『未定』）」
- **発言していないことが混ざる** → 「原文にない内容を追加しない。要約は原文の語を優先して使う」
- **長さが安定しない** → 文字数を数値で指定

雛形の出力形式:
```
### 決定事項（決定者を併記）
### ToDo（担当者 / 期限 / 内容）
### 論点と結論に至らなかった点
### 参考: 主要な発言（原文引用）
```

---

## D. 分類・抽出・データ処理（自動化で一番使う）

必須: B2 B4 B6 B7 B8 B9

落とし穴と対策:
- **カテゴリ定義が曖昧** → 各カテゴリに「含む例」「含まない例」を1つずつ書く
- **該当なしを無理に分類** → 「どれにも当てはまらない場合は `other` を返す。推測で割り当てない」
- **出力に前置きが混ざる** → 「JSONのみを出力。コードブロック記法・説明文を付けない」
- **根拠が追えない** → 各項目に `evidence`（原文の引用）を持たせる
- **件数が入力と合わない** → 「入力の件数と出力の件数を一致させる」

雛形:
```
入力の各行を、次の定義で分類する。
- A: {{定義}}（例: {{含む}} / 非該当例: {{含まない}}）
- B: ...
- other: 上記のいずれにも該当しない
出力は次のJSONのみ。入力の件数と出力配列の長さは必ず一致させる。
{"results":[{"index":1,"label":"A|B|other","confidence":0.0-1.0,"evidence":"原文の該当箇所"}]}
判断に迷う場合は confidence を0.6未満にし、label は推測せず other にする。
```

## E. 文書作成（提案書・報告書・メール・仕様書）

必須: B1 B2 B3 B6 B7 ／ 推奨: B9（社内の良い文例）

落とし穴と対策:
- **読み手が決まっていない** → 読者の役職・前提知識・関心事を明記
- **一般論で埋まる** → 「入力に含まれる固有の事実を必ず1段落に1つ以上使う」
- **意思決定に必要な情報が抜ける** → 完了条件に「費用・期間・リスク・代替案を含む」を入れる
- **社内文体と合わない** → 既存文書を1〜2本 B9 に貼る（最も効果が大きい）

---

## F. レビュー・批評（文章、設計、コード、企画）

必須: B1 B2 B6 B7 B8

落とし穴と対策:
- **褒めて終わる** → 「重大度（高/中/低）を必ず付け、高が0件ならその理由を書く」
- **指摘が抽象的** → 「各指摘に『該当箇所の引用』『なぜ問題か』『修正案の具体文』の3点を必須」
- **好みと誤りの混同** → 「『誤り』『規約違反』『好みの提案』を分けて記載」
- **件数が発散** → 「重要な順に最大{{N}}件」

---

## G. 顧客対応・問い合わせ返信

必須: B1 B3 B4 B6 B7 B8 ／ RISK高の安全ブロック

落とし穴と対策:
- **規約にない約束をする** → 「返金・納期・補償について、提供資料に記載がない条件は述べない。不明な場合は『確認のうえ回答』とする」
- **謝罪の過不足** → 「事実として当方に非がある場合のみ謝罪し、原因不明の段階では遺憾表明にとどめる」
- **エスカレーション基準なし** → 「{{条件}}に該当する場合は回答を作らず `ESCALATE: 理由` を出力する」

---

## H. 変換・翻訳・リライト

必須: B2 B4 B6 B7 B9

落とし穴と対策:
- **勝手に要約・削除する** → 「情報の追加・削除をしない。1対1で変換する」
- **用語がぶれる** → 用語集を入力に含め「用語集の訳語を優先する」
- **原文の誤りを直してしまう／直さない** → どちらの方針か明記

---

## I. コード（生成・修正・レビュー）

必須: B2 B3 B6 B7 B8

落とし穴と対策:
- **動くが要件外のものまで作る** → 「依頼された変更のみ行う。リファクタリング・抽象化・追加機能を勝手に入れない」
- **テストに合わせた場当たり実装** → 「テストを通すためのハードコードや特殊分岐を書かず、一般解を実装する」
- **既存コードを読まずに推測** → 「参照するファイルは必ず読んでから回答する。未確認のコードについて断定しない」
- **前提環境が不明** → 言語・バージョン・依存・実行環境を前提に明記

## J. AIエージェント（ツール利用・自律実行）

必須: 全ブロック + ブロック10〜13 → `agents.md` を参照。

最低限の追加:
- ツールをいつ使う/使わないか
- 停止条件（完了・失敗・人間に確認）
- 不可逆操作の事前確認ルール
- 進捗と状態の記録先

## K. LLM評価者（LLM-as-a-judge）

必須: B2 B4 B6 B7 B9

落とし穴と対策:
- **基準が主観** → 各評価軸に1〜5点のルーブリック（各点の定義文）を書く
- **順序バイアス・長さバイアス** → 「長さや流暢さではなく基準の充足のみで採点する」「候補の提示順は評価に影響させない」
- **点数だけで再現性なし** → 「各点数に、根拠となる原文の引用を1つ付ける」
- 出力は必ず機械可読（JSON）にし、`score` と `reason` を分ける
