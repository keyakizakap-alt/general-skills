# モデルの成長に追随する設計

**核心**: モデルが賢くなるほど、良いプロンプトは**短くなる**。世代が上がったときにやるべきことは追記ではなく**削除**である。
プロンプトが劣化する最大の原因は、古い世代のために書いた「引き出すための足場（scaffolding）」が残り続けることにある。

この原則を運用に落とすため、このスキルは3つの仕組みを持つ。

1. **能力ティア** — モデル名ではなく、観測できる能力で分岐する（名前は陳腐化するが、能力の階段は残る）
2. **減算リスト** — 世代が上がったら最初に消すものを固定する
3. **移行手順** — 削除を安全に行う測定手順

---

## 1. 能力ティア

新しいモデルが出たら、名前ではなく `assets/capability-probe.md` で能力を確認し、次のどれかに割り当てる。

| ティア | 観測される特徴 | 設計の重心 |
|---|---|---|
| **T0 軽量** | 指示を落とす、長い指示で崩れる、JSONを外す、否定形を守れない | **引き出す**: 短文・1文1命令・例を多く |
| **T1 標準** | 指示追従は安定。内蔵推論なし。CoT指示や few-shot が明確に効く | **形を作る**: 手順・例・形式指定 |
| **T2 推論内蔵** | 思考が内蔵され、複雑な問いで自動的に深く考える。思考量の制御パラメータを持つ | **抑える**: 冗長さ・過剰探索の抑制、完了条件 |
| **T3 自律エージェント** | 長時間タスク、複数ターンのツール利用、状態保持、サブエージェント | **境界を引く**: 停止条件・確認条件・スコープ |

ティアが上がるほど、設計の仕事は「能力を引き出す」から「**能力を暴走させない**」に移る。

### ティア別の加算・減算

| | T0 | T1 | T2 | T3 |
|---|---|---|---|---|
| 役割設定 | 最小（1行） | 1〜2文 | 1〜2文 | 責務の限定を明記 |
| 手順の分解 | 5ステップ以内で細かく | 必要なら書く | **達成物だけ書き、考え方は書かない** | 計画の提示を求める |
| CoT指示（段階的に考えて） | 効くことがある | 効く | **不要。削除**（二重思考で冗長化） | 不要 |
| 例（few-shot） | 5件以上 | 3〜5件 | 1〜3件（境界事例のみ） | 出力契約の例のみ |
| 出力形式の強制 | プロンプトで厳格に | プロンプト＋例 | **API側のスキーマ機能へ委譲** | 同左 |
| 出力長の指定 | 必要 | 必要 | **必須**（世代ごとに既定の饒舌さが変わる） | 必須 |
| 強い語調（必ず/絶対に/CRITICAL） | やや必要 | 通常の指示で足りる | **過剰反応を招くため削除** | 削除 |
| 完了条件・停止条件 | あれば良い | 必要 | 必要 | **最重要** |
| スコープ固定 | 不要なことが多い | あれば良い | **必要**（過剰実装が起きる） | 必須 |
| 検証手段の提供 | — | あれば良い | 必要 | **必須**（自己検証できないと長時間タスクが破綻） |

## 2. 減算リスト（世代が上がったら最初に消す）

| 消すもの | なぜ消すか |
|---|---|
| 「段階的に考えて」「ステップバイステップで」 | 推論内蔵世代では思考が二重になり、冗長化・遅延を招く。思考量はAPIパラメータで制御する |
| 形式模倣のための大量の few-shot | 少数で足りる。例が多いほどその表層に過剰適合する |
| 「必ず」「絶対に」「CRITICAL」「手を抜くな」「迷ったらツールを使え」 | 新しい世代は指示に忠実なため、過剰にツールを呼び、過剰に探索する。通常の指示文に戻す |
| 長い役割演技・煽り文句（「あなたは世界最高の…」） | 余計な語は品質を下げる。役割は1〜2文で足りる |
| 防御的な再掲・言い換えの重複 | 指示の矛盾を生む温床になる。1箇所に統合する |
| 出力整形の自前強制（「JSONだけ出せ」を何度も書く） | 構造化出力機能があるならそちらが確実。プロンプトは意味の定義に集中させる |
| 応答の先頭を固定する前提の設計（プレフィル依存） | 新しい世代では非対応になることがある。形式指定に置き換える |
| 過剰に細かい手順分解 | 自分で計画できる世代では硬直化して質を下げる。達成物と制約だけ残す |

**逆に、世代が上がるほど重要になるもの（減らさない）**

- 完了条件 / 停止条件 / 人間に確認する条件 — 自律性が上がるほど事故のコストが上がる
- スコープ固定 — 賢いモデルほど「気を利かせて」範囲を広げ、過剰実装する
- 出力長の明示 — 既定の饒舌さは世代ごとに揺れる。最も再現性が壊れやすい箇所
- 根拠・出典の要求と自己検査 — 長時間タスクでは人間が逐一確認できない
- 状態と進捗の外部化 — セッションをまたぐ作業では必須

## 3. 移行手順（モデル乗り換え／新世代が出たとき）

**順序が重要。先に足すと、何が効いたか永久に分からなくなる。**

```
1. ベースライン: 代表入力を15〜30件（本番データから）固定し、現行プロンプトで実行して結果を保存する
2. 素で測る: プロンプトから足場を全部外した最小版（目的・入力・出力形式・品質基準のみ）でも同じ入力を実行する
   → 最小版で十分な項目が判明する。ここが削除の上限になる
3. 一つずつ戻す: 最小版で失敗した項目に対応するブロックだけを1つずつ戻し、都度再測定する
4. 残った失敗にだけ追記する（足すのは最後）
5. 記録する: 日付 / 対象モデル / 外したもの / 足したもの / 変化 を1行残す
```

- **変更は1度に1箇所**。まとめて変えると原因が特定できない
- 「良くなった気がする」で更新しない。同じ入力セットで比較する
- 削除して退行しなかった項目は、二度と戻さない（それは元々効いていなかった）

## 4. プロンプトに履歴を持たせる

生成したプロンプトの先頭に、棚卸しできるメタ情報を入れる。将来の自分（と後任）が削除判断できるようになる。

```
<!-- prompt: 問い合わせ分類 / v3 / 2026-09-12
     対象ティア: T2 / 検証モデル: {{モデル}} / 入力セット: tickets_30.jsonl
     前回変更: CoT指示を削除（退行なし）、出力長の明示を追加 -->
```

チャットに貼るだけの用途ではコメント行を外してよい。API・社内テンプレートに載せる場合は必ず残す。

## 5. 鮮度ポリシー（このスキル自身が腐らないための規則）

このスキルは、**腐る情報と腐らない情報を物理的に分離**している。

| ファイル | 内容 | 寿命 |
|---|---|---|
| `blocks.md` / `archetypes.md` / `pitfalls.md` / `agents.md` | モデル非依存の原則・型・失敗モード | 長い（世代が変わっても有効） |
| `model-growth.md`（このファイル） | 能力ティアと移行手順 | 長い（ティアの階段は残る） |
| `targets.md` | ベンダー・世代固有の記述 | **短い。参照日つきで記載し、定期的に再検証する** |

**運用規則**
- モデル名・バージョン固有の記述は `targets.md` にのみ書く。他のファイルには書かない
- `targets.md` の各項目には参照日と出典を付ける
- **90日経過、または対象モデルの世代が変わったら、`targets.md` を公式ドキュメントで再検証する**。再検証していない項目は「未再検証」と明示し、断定しない
- 新しい世代の情報を足すときは、古い世代向けの記述を**同時に削除するか、対象ティアを明記して残す**。積み上げない
