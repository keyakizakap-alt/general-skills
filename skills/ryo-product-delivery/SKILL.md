# ryo-product-delivery

**目的**: 「作った」ではなく「利用者が実際に使える/伝わる」状態で納品する。
推測で進めず、**現在のコードと最新の指示**を事実の起点にする。

---

## 0. 事実の優先順位（最初に必ず守る）

1. **ユーザーの最新の指示**（この会話で直近に言われたこと）
2. **現在のコード・設定・データ**（実際にリポジトリにあるもの）
3. 過去の会話・メモリ・README に書かれた希望や計画

- 過去に「欲しい」と言われた機能を、**実装済みと決めつけない**。コードで存在を確認できたものだけを「実装済み」と呼ぶ。
- 過去の希望と最新の指示が食い違う場合は最新の指示に従い、食い違いを一言で報告する。
- 判断に迷う矛盾（どちらを採っても手戻りが大きい）だけは、要点を絞って質問する。

## 1. 現状把握（コードを書く前に）

次を確認し、結果を短い表にまとめてから着手する。

| 確認項目 | 見る場所の例 |
|---|---|
| 技術スタック・起動方法 | `package.json` / `pyproject.toml` / `README` / `Dockerfile` / scripts |
| 実装済み機能（画面・API・ジョブ） | ルーティング定義、`pages/` `app/` `routes/`、APIハンドラ |
| 未実装・途中の機能 | TODO/FIXME、空のハンドラ、モック・ダミーデータ、無効化されたボタン |
| 認証・権限 | 認証ミドルウェア、セッション/トークン処理、ロール判定 |
| データ構造と所有者 | スキーマ/マイグレーション、`user_id`/`tenant_id` 等の列、RLS |
| 外部API・秘密情報 | `.env.example`、設定ファイル、APIクライアント初期化箇所 |
| 既存デザイン | デザイントークン、CSS変数、Tailwind設定、既存コンポーネント |
| テスト・Lint | テスト/型チェック/Lintのコマンドと現状の成否 |

- 「実装済み」「途中」「未着手」を区別して報告する。見ていない箇所は「未確認」と書く。
- 既存の命名・構成・コンポーネントを再利用する。同じ役割のものを新しく作らない。

## 2. 計画（長い作業のみ）

- 変更範囲・手順・完了条件（何が動けば完了か）を箇条書きで先に示す。
- 技術選定には理由・制約・リスクを一行ずつ添える。
- 次の操作は**実行前に確認を取る**: 削除・初期化・上書き／本番環境・課金・外部公開／認証情報・権限の変更／情報の不確実性が高い判断。
- **難しいアプリ**（複数画面・認証・データ分離・外部API・複数日の作業のどれかに当たる）は、`references/complex-apps.md` の「設計を固める→承認→1作業ずつ実装と検査→独立レビュー」で進める。Claude Code でワークフロー（`app-design` / `app-implement` / `verify-fix`）が使えれば使う。

## 3. 実装

### 伝わる表現
- 画面の文言は**利用者の言葉**で書く。内部用語・実装用語（例: "entity", "payload", "invalid state"）を出さない。
- ボタンは動詞で結果が分かる名前にする（「送信」より「見積もりを依頼する」）。
- エラーは「何が起きたか＋次に何をすればよいか」を書く。スタックトレースや生のAPIエラーを表示しない。
- 空状態・読み込み中・失敗時の表示を必ず用意する。
- LP・資料は「誰に・何を・なぜ今」を1画面/1枚目で伝える。1スライド1メッセージ。数字や主張には出典を付け、推測は推測と明記する。

### AI機能
- モデル名・APIの仕様・料金・機能ステータス（Preview/GA/非推奨）は記憶で書かず、公式ドキュメントで確認してから使う。確認できない場合は「未検証」と明示する。
- タイムアウト・リトライ・レート制限・失敗時のフォールバック表示を実装する。
- ユーザー入力をそのままシステムプロンプトに連結しない。出力をHTMLとして描画する場合はサニタイズする。

### デザイン（安易なAI風を避ける）
避けるもの:
- 黒/濃紺ベタ背景＋ネオン・蛍光色（シアン/マゼンタ/ライム）のアクセント
- 意味のない紫〜青のグラデーション、グロー、発光ボーダー、ガラス風カードの多用
- 絵文字や✨アイコンの装飾的な乱用、「革新的」「次世代」などの中身のない見出し
- どのサービスにも当てはまる汎用テンプレート構成（Hero＋3カラム機能紹介＋CTAだけ、など）

目指すもの:
- 既存のブランド/デザイントークンがあればそれに従う。なければ、明るい中立色の背景＋落ち着いた主色1色＋補助色1〜2色に絞る。
- 余白・文字サイズ・行間で階層を作る（装飾で作らない）。本文は日本語で16px以上・行間1.7前後を目安にする。
- コントラスト比は WCAG AA（本文 4.5:1）以上を確保する。
- ダークモードは要件がある場合に、ライトと同等の品質で用意する（黒背景を既定にしない）。
- 作る前の決め方（参照点・質感・主役、色・文字・余白・形の決定）と仕上げの兆候検査は `anti-ai-look` スキルに従う（使える環境なら）。

## 4. 動作検証（完了宣言の前に必ず実施）

実際に起動して確認する。起動できない場合は、その理由と未検証項目を明記する。

### 4-1. 表示（スマホ / PC）
- 最低でも幅 **375px（スマホ）** と **1280px以上（PC）** で確認する。可能ならPlaywright等でスクリーンショットを撮って目視する。
- 横スクロールが発生しない／文字や画像がはみ出さない／タップ領域が44px程度ある／固定ヘッダーが内容を隠さない。

### 4-2. ボタン・操作の実動作
- 画面上の**すべてのボタン・リンク・フォーム**を実際に押し、期待した結果（画面遷移・保存・API呼び出し・表示更新）が起きることを確認する。
- 見た目だけで何も起きないボタン、`href="#"`、未接続のハンドラ、モックのままの処理を残さない。残す場合は「未実装」と明示する。
- 二重送信、入力エラー、ネットワーク失敗時の挙動も確認する。

### 4-3. 認証・データ分離
- 未ログイン状態で保護ページ・保護APIにアクセスできないこと（画面だけでなく**API側でも**拒否されること）。
- ユーザーAでログインし、ユーザーBのデータ（ID直打ち・URL改変・API直叩き）を**読めない・書けない・消せない**こと。
- 権限判定はサーバー側で行う。フロントの表示制御だけに頼らない。DBにRLS等がある場合は有効になっているかを確認する。

### 4-4. APIキー・秘密情報
- APIキーをフロントエンドのコード・バンドル・`NEXT_PUBLIC_`/`VITE_` 等の公開用環境変数に置かない。外部APIはサーバー経由で呼ぶ。
- `.env` 等がコミット対象外（`.gitignore`）であること、`.env.example` にはダミー値のみであることを確認する。
- ログ・エラーメッセージ・レスポンスにキーやトークンが出ないことを確認する。
- 差分に秘密情報らしき文字列（`sk-`, `AKIA`, `AIza`, `-----BEGIN` など）が含まれていないか検索する。

### 4-5. 自動チェック
- リポジトリにあるテスト・型チェック・Lint・ビルドを実行し、結果をそのまま報告する（失敗を隠さない）。

## 5. 報告

結論を先に書き、次の順でまとめる。

1. **できたこと**（利用者から見て何ができるようになったか）
2. **検証結果**（表示・ボタン・認証/データ分離・APIキー・自動チェックごとに ✅/⚠️/未確認）
3. **未実装・既知の制約・リスク**
4. **次にやるとよいこと**（あれば）

「動くはず」「おそらく大丈夫」で終えない。確認したことと確認していないことを分けて書く。
