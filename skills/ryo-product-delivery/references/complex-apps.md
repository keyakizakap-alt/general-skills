# 難しいアプリの進め方

対象: 複数画面・認証・データ分離・外部API・複数日にまたがる作業のどれかに当たるもの。技術スタックは問わない（現状調査で検出したものに合わせる）。

## 全体の流れ

| 段階 | 成果物 | 利用者の関与 |
|---|---|---|
| 1. 現状調査 | スタック、起動・テスト・検査コマンド、実装済み機能、認証、データの所有者、リスク、未確認事項 | なし |
| 2. 設計案 | 優先順位の違う2〜3案（MVP優先 / リスク優先 / 利用者優先） | なし |
| 3. 仕様書と設計判断記録 | `docs/spec/<名前>.md`、`docs/adr/NNNN-<名前>.md`、作業分解 | **承認する** |
| 4. 実装 | 1作業ずつ実装→検査→修正 | 停止時に判断 |
| 5. 独立レビュー | 正しさ / セキュリティ・データ分離の2観点、必要なら画面確認 | 指摘の扱いを決める |
| 6. 報告 | 変更点、検査結果、未確認事項、次の一手 | commit / デプロイを承認する |

段階3の承認を挟むのは、作り始めてからの手戻りが最も高くつくため。

## Claude Code での実行（ワークフローが使える場合）

プラグイン `general-skills` を入れているか、リポジトリの `.claude/workflows/` に置いてある場合:

```text
app-design ワークフローで request="<作りたい機能>" を設計して
（仕様書を確認・承認したら）
app-implement ワークフローで spec="docs/spec/<名前>.md" を実装して
verify-fix ワークフローで command="npm test" が通るまで直して
```

- Pro プランでは `/config` の Dynamic workflows を有効にする（公式 https://code.claude.com/docs/en/workflows 、参照日 2026-10-05）。1回の実行は作業2件までを既定にしている（`maxTasks` で変更）。一発で通れば5エージェント、修正が入ると増える。
- ワークフローの実行中は質問できない。承認が必要な区切りでワークフローを分けている。
- 使用量はエージェントの数に比例して増える。最初は小さい範囲（1機能・1ディレクトリ）で試す。

ワークフローが使えない環境（claude.ai のチャット等）では、同じ段階を1つずつ順に行う。

## 仕様書に必ず書くこと

- 目的と対象外（やらないこと）
- 画面 / API / ジョブの一覧と入出力
- データ構造と所有者（`user_id` / `tenant_id`、RLS 等）、権限の判定場所
- エラー時・空の状態・権限が無い場合の挙動
- 受け入れ条件（検査で判定できる形）
- 作業分解: 1作業 = 変更するファイルの集合が重ならない単位。依存関係つき
- 検査コマンド（実在するもの。無ければ「未設定」と書き、先に用意する）

## 設計判断記録（ADR）

重要な判断ごとに1ファイル。背景・選択肢・決定・結果（良い点と代償）を書く。後から「なぜこうしたか」を辿れるようにする。

## 停止条件

- 同じ失敗が2回続いたら止める。修正は1作業あたり2回までを既定にする
- 止まったら、原因の仮説・試したこと・不足情報を報告する。テストの削除や検査の緩和で通さない

## 承認が必要な操作

依存パッケージの追加、DBマイグレーションの実行、ファイル削除、commit / push、デプロイ、課金・外部公開、認証情報や権限の変更。
